# Codex Refactor Orchestrator 通用使用说明

本说明面向第一次使用 Codex Skill 和 subagents 的用户。

# Part A：快速开始

## 1. 工作方式

```text
Parent Agent
├── 可选：Explorer mini（只读调查）
├── 可选：Executor mini（限定实现与测试）
└── Parent Review 与验收
```

- Parent：理解需求、检查仓库、冻结契约、决定是否委派、Review 和验收。
- Explorer：隔离全仓搜索、调用链、引用、测试日志等 read-heavy 上下文。
- Executor：在边界和契约明确后实现代码、测试和机械自查。

Skill 不追求最大 subagent 数量。委派只有在收益大于协调成本时才发生。

## 2. 安装

```bash
bash install.sh /path/to/your-project
```

目标必须是 Git 仓库根目录。推荐使用 `bash install.sh`，避免脚本无执行权限时出现：

```text
zsh: permission denied: ./install.sh
```

安装器会写入：

```text
.agents/skills/refactor-orchestrator/
.codex/agents/refactor-explorer-mini.toml
.codex/agents/refactor-executor-mini.toml
.codex/config.toml
```

已有 `.codex/config.toml` 时会先备份，保留现有值，只补缺失字段。

默认配置：

```toml
[agents]
max_threads = 4
max_depth = 1
job_max_runtime_seconds = 1800
```

- `max_threads`：并发上限，不是每次启动数量。
- `max_depth = 1`：只有 Parent 可以创建直接 subagent。
- `job_max_runtime_seconds`：批量 worker 的默认最长运行时间。

## 3. 当前模型配置

默认模型组合：

| 角色 | 当前模型 | Reasoning | 配置位置 |
| --- | --- | --- | --- |
| Parent | `gpt-5.5` | 由启动或 Codex 配置决定 | `-m/--model`、`/model`、Codex `config.toml` |
| Explorer mini | `gpt-5.4-mini` | `medium` | `.codex/agents/refactor-explorer-mini.toml` |
| Executor mini | `gpt-5.4-mini` | `medium` | `.codex/agents/refactor-executor-mini.toml` |

当前两个 mini 配置文件都包含：

```toml
model = "gpt-5.4-mini"
model_reasoning_effort = "medium"
```

Explorer 另外配置：

```toml
sandbox_mode = "read-only"
```

Executor 另外配置：

```toml
sandbox_mode = "workspace-write"
```

### 3.1 临时修改 Parent 模型

启动新 Session 时指定：

```bash
codex -m gpt-5.5
# 等同于
codex --model gpt-5.5
```

例如临时改为：

```bash
codex -m gpt-5.4
```

这种方式只影响本次启动。

### 3.2 在当前 Session 中切换 Parent 模型

在 Codex CLI 输入：

```text
/model
```

然后从当前账号和 Codex 版本可用的模型中选择。该选择作用于当前活动 Session，不会自动修改磁盘上的配置文件。

### 3.3 修改默认 Parent 模型

用户级默认配置位于：

```text
~/.codex/config.toml
```

受信任项目也可以在项目根目录使用：

```text
.codex/config.toml
```

加入或修改：

```toml
model = "gpt-5.5"
```

启动时的 `-m/--model` 会覆盖配置文件中的默认模型。

### 3.4 修改 Explorer 或 Executor 模型

编辑目标项目中的：

```text
.codex/agents/refactor-explorer-mini.toml
.codex/agents/refactor-executor-mini.toml
```

例如把 Executor 改为 `gpt-5.4`：

```toml
model = "gpt-5.4"
model_reasoning_effort = "high"
```

或者继续使用 mini，但调整 reasoning：

```toml
model = "gpt-5.4-mini"
model_reasoning_effort = "low"
```

模型和 reasoning 组合是否可用，以当前 Codex 版本、账号计划和认证方式为准。

### 3.5 为什么不建议删除 mini 的 `model`

如果 custom agent 配置中省略 `model`，它可能继承 Parent Session 的模型。这样会导致：

- Explorer/Executor 使用更昂贵的 Parent 模型；
- 原本的 Parent + mini 成本分工失效；
- 不同启动方式下 child 行为不一致。

因此推荐显式保留 mini 的 `model`。

### 3.6 修改模型后的操作

修改 Parent 或 mini 模型后：

1. 保存 TOML；
2. 新建 Codex Session；
3. 重新执行：

```bash
bash .agents/skills/refactor-orchestrator/scripts/validate-install.sh
bash .agents/skills/refactor-orchestrator/scripts/runtime-probe.sh
```

4. 首次委派时检查实际 spawning 结果。

静态 TOML 和 runtime probe 只能证明预期配置，不能单独证明某次 child 实际使用了指定模型。无法独立验证时，应报告 `not independently verified`，而不是把配置值当作运行事实。

### 3.7 已安装项目与源仓库的关系

修改 `codex-refactor-orchestrator` 源仓库中的 TOML，不会自动修改已经安装到其他项目的副本。

需要：

- 重新运行安装脚本；或
- 手动同步 `.codex/agents/*.toml` 和 Skill 文件。

重新安装前，先确认目标项目是否对 mini 配置做过项目级定制，并做好备份。

## 4. 验证与启动

```bash
cd /path/to/your-project
bash .agents/skills/refactor-orchestrator/scripts/validate-install.sh
bash .agents/skills/refactor-orchestrator/scripts/runtime-probe.sh
codex -m gpt-5.5
```

静态配置和 runtime probe 只能说明预期配置，不能单独证明实际 child model 或有效权限。

## 5. 第一次 Prompt

```text
Use the refactor-orchestrator skill.

Explicitly decide whether delegation is justified under the Skill rules.
If justified, explicitly spawn the selected configured subagent or subagents.
If not justified, proceed with the Parent only and record that zero subagents
were selected.
Do not rely on implicit delegation.

Plan and execute only <Task or Stage ID> from:
<task-list-path>

Read repository instructions and inspect current code first.
Freeze architecture and public contracts before Executor delegation.
Use bounded Task Cards and dependency batches.
Review the actual worktree, git diff, and verification output.
Do not mark completion without evidence.
```

没有 TaskList 时，先由 Parent 创建临时分阶段计划，再决定是否委派。

# Part B：委派决策

## 6. 先判断是否允许委派

Executor 委派前必须同时满足：

- 目标和输出明确；
- 允许/禁止路径可列出；
- 上游依赖完成；
- 公共契约已冻结；
- 验证命令和停止条件明确。

未解决的领域模型、事实源、迁移策略、权限策略和算法语义不能交给 mini 自行决定。

## 7. 再判断是否值得委派

至少需要一个明显收益，并且收益大于协调和上下文传递成本：

1. 隔离大量只读上下文；
2. 用低成本 Agent 承担机械工作；
3. 安全并行互不重叠的任务；
4. 显著降低高成本返工风险。

不满足时由 Parent 直接执行，记录 `0 subagents selected`。

## 8. Agent 软预算

```text
普通任务：0–1 个 subagent
独立写入：最多 2 个 Executor
大型只读审计：最多 3 个 Explorer
```

这是默认软预算。超出时 Parent 必须说明理由。

## 9. 风险与执行强度

| 风险 | 默认强度 | 方式 |
|---|---|---|
| M1 | lean | Parent 直接做或 1 个 Executor |
| M2 | standard | Parent 冻结契约，默认 1 个 Executor |
| M3 | assurance | Parent 主导，mini 只做严格限定支持 |

Parent 可以覆盖默认强度，但必须记录原因。

# Part C：上下文和同步

## 10. Parent 读取什么

Parent 读取：

- 根级和适用的仓库规则；
- TaskList、RFC、架构和迁移文档；
- 分支、基线、未提交修改；
- 当前实现、测试和正式事实源。

## 11. 子 Agent 读取什么

子 Agent 只读取：

- Task Card；
- 适用的根级或嵌套 `AGENTS.md`；
- 明确范围内的实现文件；
- 直接受影响的测试；
- 冻结契约和上游 handoff。

不要让每个 child 重读完整 TaskList 和所有全局文档。Task Card 控制范围；代码和测试仍是实现事实。发现冲突时停止并升级给 Parent。

## 12. Task Card

至少包含：

- Task ID、风险和单一目标；
- 依赖和基线；
- 必读文件和冻结契约；
- 允许/禁止路径；
- 实现要求；
- 测试、lint、build、migration 命令；
- 验收和升级条件；
- 结构化 handoff。

不得只发送“实现这个 Stage”。

## 13. 并行安全

允许并行必须满足：

- 写入路径不重叠；
- 不修改同一公共契约；
- 不依赖对方未提交结果；
- 集成顺序明确；
- 可回滚。

以下必须串行：

```text
领域模型
→ Migration
→ API/Schema
→ 生成类型/前端类型
→ 集成测试
```

共享路由、状态、表、Schema、删除和兼容退役也必须串行。

# Part D：运行证据与可靠性

## 14. Runtime Truth

始终需要证据的内容：

- 命令和测试已执行；
- diff 和文件已修改；
- migration 已应用或验证；
- 验收条件满足；
- Task 或 Stage 完成。

模型、有效权限和 spawning 细节只有可验证时才报告。无法验证时省略或写明 `not independently verified`。

仅在以下情况下使用 single-controller fallback：

- native spawning 不可用；
- child 创建失败；
- 任务依赖的权限边界无法保证。

只是不知道 child 的确切模型名称，不必自动 fallback；应报告模型未独立验证。

严格只读 Explorer 的权限无法保证时，不要创建该 Explorer，由 Parent 完成调查。

## 15. Parent Review

Parent 必须检查：

- 真实工作区和完整 diff；
- 行为与原始需求；
- 前端/后端/数据库/运行契约；
- migration 和 rollback；
- 事实源唯一性；
- 错误和 partial state；
- 测试质量；
- legacy 退役条件；
- 越界改动。

子 Agent 的 `completed` 不等于验收通过。

## 16. 最多三轮

```text
第 1 轮：初始实现
第 2 轮：定向修复
第 3 轮：最终限定修复
```

第三轮仍失败后停止、保留证据并标记阻塞，不扩大范围强行完成。

## 17. 临时状态目录

```text
.codex/refactor-state/<stage-id>/
├── stage-plan.md
├── manifest.yaml
├── contracts/
├── tasks/
├── handoffs/
├── reviews/
└── artifacts/
```

使用 bundled scripts 保存每轮 diff、测试、结果和 Review。

# Part E：常见问题

## 没有创建 subagent，Skill 是否生效？

可能生效。Parent 应明确记录委派决策；不满足门禁时，`0 subagents` 是正确结果。

## 什么任务最适合 Explorer？

未知调用链、全仓 legacy 搜索、重复事实源、迁移历史、删除前引用、测试/日志分类。

## 什么任务最适合 Executor？

契约已冻结、范围明确、测试命令已知的 UI、API、CRUD、脚本、fixture、机械迁移和文档同步。

## 如何控制额度？

- 优先 Parent 直接完成小任务；
- 优先委派 read-heavy 和机械工作；
- 默认 0–1 个 child；
- child 不重复读取全局文档；
- 一个 Executor 完成实现、测试和机械自查；
- 每个 Task 最多三轮；
- 每个 Stage 或紧密任务组使用新的 Parent Session。
