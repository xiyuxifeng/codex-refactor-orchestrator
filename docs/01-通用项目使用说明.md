# Codex Refactor Orchestrator 通用使用说明

本说明面向第一次使用 Codex Skill 和 subagents 的用户。

# Part A：快速开始

## 1. 它是怎么工作的？

```text
GPT-5.5 主 Agent
├── 可选：refactor-explorer-mini
├── refactor-executor-mini
└── GPT-5.5 Review 与 Stage 验收
```

- GPT-5.5：理解需求、检查仓库、决定架构、冻结契约、Review 和验收。
- Explorer mini：只读调查调用链、旧入口、数据源、测试和引用。
- Executor mini：在边界明确后实现代码、补测试、运行 lint/typecheck，并返回交接结果。

## 2. 安装

从本项目目录运行：

```bash
bash install.sh /path/to/your-project
```

推荐使用 `bash install.sh`，这样不依赖脚本的可执行权限，可避免：

```text
zsh: permission denied: ./install.sh
```

目标项目会新增：

```text
.agents/skills/refactor-orchestrator/
.codex/agents/refactor-explorer-mini.toml
.codex/agents/refactor-executor-mini.toml
.codex/config.toml
```

### 已有 `.codex/config.toml` 时

安装脚本会自动安全合并，不需要用户先手工编辑：

1. 创建时间戳备份；
2. 保留已有配置和值；
3. 只补充缺失的 `[agents]` 和缺失字段；
4. 在终端输出新增和保留的字段。

备份示例：

```text
.codex/config.toml.backup-20260611-153000
```

只有以下情况需要手工处理：

- 系统没有 `python3`；
- 原配置文件语法异常；
- 希望修改本项目的默认值；
- 安装输出提示合并失败。

## 3. `[agents]` 配置说明

```toml
[agents]
max_threads = 4
max_depth = 1
job_max_runtime_seconds = 1800
```

### `max_threads = 4`

同一父 Session 最多可同时运行的 Agent 线程数量，包括并发 subagents。

- `4` 是并发上限，不是要求每次创建 4 个 Agent；
- Skill 默认仍遵循“最小 Agent 数量”原则；
- 值越大，并行能力越强，但文件冲突、Token 消耗和上下文开销也可能增加；
- 对大多数重构项目，`3` 或 `4` 比较稳妥。

如果目标项目已有：

```toml
max_threads = 2
```

安装脚本会保留 `2`，不会改成 `4`。

### `max_depth = 1`

Agent 委派的最大嵌套深度。

- `1` 表示只有 GPT-5.5 主 Agent 可以创建直接 subagent；
- Explorer 或 Executor 不能继续创建孙 Agent；
- 这样可以避免递归委派、不可控并发和额外 Token 消耗；
- 本 Skill 不建议将该值提高到 `2` 以上。

### `job_max_runtime_seconds = 1800`

批量 Agent worker 的默认最长运行时间，单位为秒。

- `1800` 等于 30 分钟；
- 主要用于 `spawn_agents_on_csv` 一类批量 worker；
- 不是所有普通 subagent 的统一强制超时；
- 大型批处理可以适当提高，小型任务通常无需修改。

## 4. 验证安装

进入目标项目根目录：

```bash
cd /path/to/your-project

bash .agents/skills/refactor-orchestrator/scripts/validate-install.sh
bash .agents/skills/refactor-orchestrator/scripts/runtime-probe.sh
```

- `validate-install.sh`：检查 Skill、Agent TOML 和安装路径。
- `runtime-probe.sh`：检查当前 Codex 环境是否具备运行条件。

静态配置正确，不代表运行中的子 Agent 一定使用 GPT-5.4 mini，仍需在 Codex 中查看实际 Agent 信息。

## 5. 启动主 Session

```bash
codex -m gpt-5.5
```

建议一个 Stage 使用一个新的主 Session。

## 6. 第一次使用 Prompt

### 已有 TaskList

```text
Use the refactor-orchestrator skill.

Choose and explicitly spawn subagents according to the Skill rules.
Do not rely on implicit delegation.
Use the minimum viable number of agents.

Plan and execute <Stage ID> from:
<task-list-path>

Requirements:
1. Read repository instructions first.
2. Inspect the current repository before planning.
3. Freeze architecture and public contracts before spawning executors.
4. Delegate only bounded tasks to refactor_executor_mini.
5. Execute by dependency batch and wait for each batch.
6. Preserve the required diff, test, result, and review artifacts.
7. Review the actual git diff and verification output.
8. Do not mark the Stage complete until every exit criterion has evidence.
```

### 没有 TaskList

```text
Use the refactor-orchestrator skill.

Choose and explicitly spawn subagents according to the Skill rules.
Do not rely on implicit delegation.
Use the minimum viable number of agents.

Create a staged implementation plan for this request:
<your request>

Inspect the repository first.
Define the current source-of-truth, target behavior, risks,
task dependencies, verification commands, and acceptance criteria.
Then delegate only bounded implementation tasks to mini subagents.
```

## 7. Skill 会自动处理什么？

1. 读取仓库规则和需求；
2. 检查当前实现；
3. 判断是否需要 Explorer；
4. 冻结架构、接口和数据契约；
5. 生成 Task Card；
6. 显式创建 mini subagent；
7. 按依赖批次执行；
8. 保存每轮 diff 和测试证据；
9. GPT-5.5 Review；
10. Stage 验收。

你不需要每次手工决定使用 Explorer 还是 Executor。

## 8. 你需要处理什么？

通常只在以下情况介入：

- TaskList 和现有实现存在产品方向冲突；
- 需要在多个业务方案中做取舍；
- 数据迁移可能丢失信息；
- Stage 验收失败且不是简单代码错误；
- native subagent 或实际模型无法验证；
- Agent 请求扩大原任务范围。

## 9. 如何确认 subagent 真的生效？

观察 Codex 是否显示：

- 实际创建了 `refactor-explorer-mini` 或 `refactor-executor-mini`；
- 子 Agent 模型为 GPT-5.4 mini；
- Explorer 保持只读；
- Executor 只修改允许范围；
- GPT-5.5 检查了真实 `git diff` 和测试结果。

# Part B：工作原理

## 10. 推荐执行流程

```text
GPT-5.5 读取需求与代码
→ 按需调用 Explorer mini
→ GPT-5.5 冻结架构和契约
→ 生成 Task Cards
→ Executor mini 分批实现与测试
→ GPT-5.5 检查真实 diff
→ GPT-5.5 做语义 Review
→ Stage 验收
```

## 11. 什么时候使用 Explorer？

适合：

- 不清楚真实调用链；
- 需要全仓搜索旧入口；
- 存在重复 API、Schema 或数据源；
- 删除前需要确认引用。

不适合：

- 已知只涉及 1～3 个文件；
- 接口和路径已经明确；
- 只是局部修复。

默认不启动 Explorer。

## 12. 什么时候使用 Executor？

必须先满足：

- 只有一个明确目标；
- 契约已经冻结；
- 允许和禁止修改范围明确；
- 上游依赖已完成；
- 测试命令明确；
- 冲突时有停止条件。

## 13. 最小 Agent 原则

```text
已知局部任务：0 Explorer + 1 Executor
未知跨模块任务：1～3 Explorer，之后默认 1 Executor
```

小型任务也可能完全不创建 subagent，由 GPT-5.5 直接完成。

## 14. 并行与串行

可以并行：

- 多个互不重叠的只读调查；
- 前端页面和独立后端测试；
- 不共享公共契约的模块。

必须串行：

```text
领域模型
→ 数据库 Migration
→ API Schema
→ 前端类型
→ 集成测试
```

## 15. Agent 如何同步？

1. 主 Agent 传递 Task Card 和冻结契约；
2. 子 Agent 读取共享工作区；
3. 子 Agent 写入代码并返回结构化结果；
4. Handoff 记录变更、测试和风险；
5. 主 Agent 检查 `git status`、`git diff` 和测试输出；
6. 上游验收后再启动依赖任务。

# Part C：可靠性与高级使用

## 16. 状态目录

```bash
bash .agents/skills/refactor-orchestrator/scripts/init-refactor-state.sh stage-1
```

## 17. 每轮产物

```bash
bash .agents/skills/refactor-orchestrator/scripts/capture-round-artifacts.sh TASK_ID ROUND
```

保存 diff、测试日志、Git 状态、执行结果和 Review。

## 18. 最多三轮修复

```text
第 1 轮：初始实现
第 2 轮：定向修复
第 3 轮：最终受限修复
```

第三轮仍失败后必须停止，交回 GPT-5.5 或用户。

## 19. Single-controller fallback

native subagents、实际模型或 Explorer 权限无法验证时：

- GPT-5.5 保持唯一控制器；
- 继续生成 Plan、契约和 Task Card；
- 输出手工启动 mini Session 的命令；
- 不得声称已经使用 mini subagent。

## 20. Review

普通 Stage 可以由当前 GPT-5.5 主 Session Review。

大型或高风险 Stage 建议新开 GPT-5.5 Review Session。

# Part D：常见问题

## 21. Skill 没有被加载

确认以下路径存在：

```text
.agents/skills/refactor-orchestrator/SKILL.md
```

## 22. 没有创建 subagent

小型任务可以由 GPT-5.5 直接完成。适合委派的任务应在 Prompt 中包含：

```text
Choose and explicitly spawn subagents according to the Skill rules.
Do not rely on implicit delegation.
```

## 23. 子 Agent 模型无法确认

进入 single-controller fallback。

## 24. Explorer 修改了文件

检查父 Session 是否使用了 unrestricted full-access/yolo 权限。

## 25. 已有 `.codex/config.toml`

直接运行安装脚本。脚本会：

- 创建备份；
- 保留已有字段和值；
- 自动补充缺失项；
- 输出合并结果。

通常不需要手工编辑。

## 26. 如何控制 Token？

- 不为已知局部任务创建 Explorer；
- 每批默认 1 个 Executor；
- 只向子 Agent 传当前 Task 必需内容；
- 不让多个 Agent 重复扫描全仓；
- 同一 Task 最多三轮；
- 一个 Stage 使用一个新的 GPT-5.5 Session。
